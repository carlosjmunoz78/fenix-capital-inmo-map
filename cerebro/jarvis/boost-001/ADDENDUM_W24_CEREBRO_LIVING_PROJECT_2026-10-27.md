## W24 · CEREBRO LIVING PROJECT

### Mission
CEREBRO itself must appear inside JARVIS as a permanent, resumable, continuously updated project.

It is not a static dashboard and not merely documentation. It is the living operational project through which Carlos, Jarvis, DeepSeek and authorised agents can inspect, understand, repair, improve and verify CEREBRO over time.

### JARVIS integration
JARVIS View 0 must expose a permanent project provisionally named `CEREBRO OS` or `CEREBRO`.

Opening that project must restore its current state and context without rebuilding discovery from scratch.

The experience should be Work-style:
- persistent project context;
- project conversation with Jarvis;
- durable tasks/jobs;
- files/artifacts/evidence;
- activity timeline;
- current objectives;
- active workstreams;
- blockers/HUMAN_REQUIRED;
- costs;
- previews/interfaces;
- links to relevant code/routes/contracts/tests;
- resumable history;
- ability to continue work naturally by voice or text.

### Living self-model
The project must consume the canonical W23 Control Map rather than maintain a separate manual model.

It should continuously expose, where authorised:
- systems and departments;
- engines/capabilities;
- agents/subagents;
- interfaces (JARVIS, Work, Neural, App Fenix, etc.);
- repositories/branches/deploy anchors;
- dependencies and reverse dependencies;
- contracts;
- tests/gates;
- environments;
- integrations;
- runbooks;
- active incidents;
- health/status;
- current projects/work items;
- changes since last verified state.

### Continuous editing model
Changes to CEREBRO must update the living project automatically through events/generation where possible.

Examples:
- new engine -> appears in map/project;
- new agent/subagent -> appears under department/ownership;
- moved/renamed path -> route index regenerated and aliases preserved;
- test added/removed -> test anchors updated;
- deployment promoted -> environment/deploy state updated;
- capability repaired -> status/evidence/changelog updated;
- dependency changed -> graph/impact index regenerated;
- interface changed -> preview/evidence linked;
- APPFACT creates a component -> project records it and its lifecycle.

Manual notes may supplement facts that cannot be derived, but must not become the primary source of truth for machine-derivable state.

### Project views
The same project may be rendered through multiple coordinated views without creating separate sources of truth:

1. `JARVIS` — conversational/executive Work-style project surface.
2. `WORK` — detailed task/artifact workspace.
3. `NEURAL` — visual dependency/agent/system graph from W23.
4. `TECHNICAL` — code/routes/contracts/tests/evidence drill-down.
5. `TIMELINE` — changes, incidents, promotions, rollbacks and learning.

All views must read/write through canonical Gateway/Jobs/Events/Registry/Map contracts rather than private client-only state.

### Audit and repair advantage
DeepSeek and other agents must use the living CEREBRO project as persistent context/navigation after W00/W23 establish the first verified state.

Subsequent work should prefer:
`project context -> MAP-001 resolver -> targeted files/contracts/tests -> execution`

over repeated broad repository rediscovery.

This should reduce token cost, discovery time, accidental edits and context loss.

### Change safety
The living project is an operational control surface, not permission to edit PROD directly.

Every repair still follows:
CONSERVAR -> ENTENDER -> ENVOLVER -> PROBAR -> MEJORAR -> MIGRAR.

The project must show environment and promotion state clearly and preserve OLD-vs-NEW, rollback, evidence and audit.

### Acceptance criteria
W24 is GREEN only when:
1. a permanent CEREBRO project exists in JARVIS;
2. it can be reopened with durable context/history;
3. it consumes the canonical W23 map/self-model;
4. Work and Neural are alternative views of the same canonical project state;
5. a real code/config/test change updates the project/map deterministically;
6. Jarvis can resolve and open a component from natural language;
7. Jarvis can create and resume a repair job from the project;
8. the project shows current state, evidence, environment and rollback anchors;
9. no secret values are exposed;
10. at least one real audit/repair demonstrates faster targeted discovery than a cold repository scan.
